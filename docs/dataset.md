# ชุดข้อมูล AOI: ที่มา (provenance) และการตรวจความถูกต้อง

เอกสารนี้อธิบายฟิลด์ `provenance` ใน `apps/web/public/aoi/{code}/manifest.json`
(งาน E9.1) — มันบอกอะไร **ไม่**บอกอะไร และเมื่อลายเซ็นของ `terrain.bin` ไม่ตรง
แล้วชั้นข้อมูลไหนถูกปิดบ้าง — และ (หัวข้อ 7, งาน E9.2) `datasetVersion` กลายเป็น
prefix ของ URL ของ tile ได้อย่างไร อะไรทำให้มันต้องเปลี่ยน และทำไม prefix เก่า
ถึงลบไม่ได้

สัญญาของชนิดข้อมูลอยู่ที่ `packages/shared-types/src/aoi.ts`
(`AoiProvenance`, `AoiLayerProvenance`, `AoiProvenanceLayer`)

---

## 1. รูปร่างของ `provenance`

```jsonc
"provenance": {
  "datasetVersion": "2026-08-17",           // รุ่นของชุดข้อมูล = prefix ของ tile URL (E9.2, หัวข้อ 7)
  "generatedAt": "2026-08-20T03:46:11.000Z", // เวลาที่ "ไฟล์ manifest นี้" ถูกเขียน
  "sources": {
    "terrain":   { "builtAt": "2026-08-17T02:51:03.000Z", "sourceIds": ["copernicus-dem"] },
    "buildings": { "builtAt": "2026-08-17T03:16:06.000Z", "publishedAt": "2026-08-15T20:21:20.000Z", "sourceIds": ["osm"] },
    "roads":     { "builtAt": "2026-08-17T03:32:44.000Z", "publishedAt": "2026-08-15T20:21:20.000Z", "sourceIds": ["osm"] },
    "water":     { "builtAt": "2026-08-17T03:32:44.000Z", "publishedAt": "2026-08-15T20:21:20.000Z", "sourceIds": ["osm"] },
    "trees":     { "builtAt": "2026-08-17T05:00:43.000Z", "sourceIds": ["worldcover"] }
  },
  "checksums": { "terrain.bin": "…64 hex…" }
}
```

ทั้งก้อนเป็น **optional**: manifest ที่สร้างก่อน E9.1 ไม่มีฟิลด์นี้ และฝั่ง client
ต้องทำงานได้เหมือนเดิมทุกประการเมื่อมันหายไป — ตลอดไป ไม่ใช่ชั่วคราว

### `generatedAt` ≠ `builtAt`

- `generatedAt` = manifest ถูกเขียนเมื่อไหร่
- `builtAt` = artefact **ของชั้นนั้นเอง** ถูกผลิตเมื่อไหร่

การรีเฟรช manifest วันนี้ทับ artefact ที่ build เมื่อสามวันก่อนเป็นเรื่องปกติ
สองเวลานี้จึงต่างกันได้ และความต่างนั้นคือเหตุผลทั้งหมดที่ต้องมี provenance รายชั้น
ห้ามยุบให้เหลือค่าเดียว

### `datasetVersion` — อะไรทำให้มันเปลี่ยน (E9.2)

`datasetVersion` ไม่ใช่แค่ข้อความโชว์ใต้แผนที่อีกต่อไป มันคือ segment `v/{ver}` ใน
URL ของ tile ทุกไฟล์ (`/aoi/{code}/v/{ver}/{layer}/{z}/{x}_{y}.bin`) กฎจึงเหลือข้อเดียว:

> **ไบต์ใต้ `aoi/{code}/v/{ver}/` เปลี่ยนเมื่อไหร่ `{ver}` ต้องเปลี่ยนด้วย**

เพราะ tile ถูกส่งด้วย `Cache-Control: public, max-age=31536000, immutable` —
การตอบผิดหนึ่งครั้งแก้ไม่ได้อีกหนึ่งปี ไม่มีทั้ง purge รายไฟล์ที่ถึงเบราว์เซอร์และ
ไม่มีทางบอก client ที่แคชไว้แล้วให้ถามใหม่

รูปแบบคือ `YYYY-MM-DD` และ `YYYY-MM-DD.N` เมื่อปล่อยเกินหนึ่งครั้งในวันเดียว
(`DATASET_VERSION_RE` ใน `apps/etl/src/datasetVersion.ts` และ `VERSION` ใน
`apps/web/worker/tilePath.ts` ต้องตรงกันเสมอ — รุ่นที่ฝั่ง Worker ไม่รับ = ทั้ง
prefix ตอบ 404 ทั้งที่ไบต์อยู่ครบใน R2)

**ปัญหาที่กฎนี้แก้** เดิม `refresh:manifests` หาค่าตามลำดับ `--dataset-version=` →
`provenance.datasetVersion` เดิม → `manifest.version` ส่วน `manifest.version` ถูก
สคริปต์ tile รายชั้นเขียนทับเป็นวันที่ปัจจุบันทุกครั้งที่ rebuild ชั้นใดชั้นหนึ่ง
ผลคือ rebuild ชั้นเดียวแล้ว `manifest.version` ขยับ แต่ `datasetVersion` ไม่ขยับ
ตาม → prefix เดิมเสิร์ฟไบต์ชุดใหม่ ซึ่งเป็นความล้มเหลวที่ถูกล็อกไว้หนึ่งปีพอดี

**สิ่งที่บังคับไว้ตั้งแต่ E9.2** (ทั้งสองอยู่ใน `apps/etl/src/datasetVersion.ts`):

1. **ไม่เดารุ่นอีกแล้ว** — `manifest.version` ไม่ใช่ตัวสำรองของ `datasetVersion`
   อีกต่อไป ไม่มี `--dataset-version=` และ manifest ยังไม่มีรุ่นเดิม = สคริปต์
   ล้มเหลวของจังหวัดนั้น ไม่ใช่หยิบค่าอื่นมาใส่
2. **ห้ามใช้รุ่นเดิมซ้ำเมื่อเนื้อหาเปลี่ยน — ไม่ว่ารุ่นนั้นจะเป็นรุ่นปัจจุบันของ
   manifest หรือรุ่นเก่ากว่านั้นก็ตาม** — `refresh:manifests` เก็บ
   `apps/etl/data/dataset-version-ledger.json` ไว้ต่างหาก: ประวัติลายเซ็นเนื้อหา
   (`tileContentSignature()`) ของ**ทุกรุ่น**ที่แต่ละ AOI เคยมี ไม่ใช่แค่รุ่นล่าสุด
   ตัวเดียว (`isSafeVersionReuse()` ใน `datasetVersion.ts`) — เพราะการเทียบแค่
   "รุ่นปัจจุบันของ manifest" อย่างเดียว (พฤติกรรมเดิมก่อน E9.2 รอบแก้ล่าสุด) มองไม่
   เห็นกรณีที่ผู้ใช้งานระบุ `--dataset-version=` เป็นรุ่นที่**เก่ากว่า**รุ่นปัจจุบัน
   ของ manifest ซ้ำ (พิมพ์ผิด, สคริปต์เก่าค้างอยู่, ความพยายาม rollback ที่พลาด)
   ทั้งที่เนื้อหาบนดิสก์ขยับไปเป็นของรุ่นถัดไปแล้ว — ไฟล์ ledger นี้ถูก track ใน git
   ตามปกติ (ไม่อยู่ใต้ `data/tiles`/`data/raw`/`data/work` ที่ถูก gitignore) เพื่อให้
   ประวัติการปล่อยรุ่นเดินทางไปกับ repo ไม่ใช่อยู่แค่บนเครื่องที่รันครั้งล่าสุด — "track
   ได้" ไม่พอเอง มันต้องถูก **commit จริงในทุกรอบปล่อยรุ่น** คู่กับ manifest เสมอ
   (`docs/dataset-release.md` §4 บังคับขั้นตอนนี้ไว้; review round 7 เป็นรอบที่พบว่า
   ไฟล์นี้ถูกสร้างไว้ตั้งแต่ round 6 แต่ไม่เคย commit เข้า repo เลยสักครั้ง — รายละเอียด
   ขั้นตอนดู `docs/dataset-release.md`)

   ถ้ารุ่นที่ขอเคยถูกบันทึกไว้ด้วยลายเซ็นอื่น สคริปต์จะหยุดโดยไม่เขียนไฟล์ พร้อม
   บอกรายละเอียด (ชั้นไหนขยับ ถ้าเป็นรุ่นปัจจุบันของ manifest จริง หรือลายเซ็นเดิม/
   ใหม่ ถ้าเป็นรุ่นเก่ากว่านั้น) ทางออกคือตั้ง `--dataset-version=` เป็นรุ่นใหม่
   (`--allow-version-reuse` มีไว้สำหรับกรณีเดียว: รุ่นนั้นยังไม่เคยถูกอัปขึ้น R2)

   ชั้นที่ **หายไป** (มี `builtAt` เดิมแต่คำนวณใหม่ไม่ได้) ไม่นับเป็น "เนื้อหา
   เปลี่ยน" — เกือบทุกครั้งมันแปลว่าเครื่องนี้ไม่ได้ symlink ชุด tile (clone ใหม่
   หรือ CI) จึงเตือนออกมาแต่ไม่บล็อก และ `publishedAt`/`generatedAt` ไม่ถูกนับเข้า
   ลายเซ็นเลย เพราะมันขึ้นกับว่ามี osmium/ไฟล์ pbf บนเครื่องนั้นไหม ไม่ใช่ไบต์ของ tile

### `builtAt` มาจากไหน

จาก mtime ล่าสุดของโฟลเดอร์ tile ใน `apps/etl/data/tiles/{code}/{layer}/`
(หรือจากเวลาที่จดไว้ตอน build เมื่อรันนั้นเป็นคนสร้าง artefact เอง)

| ชั้นใน manifest | โฟลเดอร์ artefact |
|---|---|
| `terrain` | `tiles/{code}/terrain` |
| `buildings` | `tiles/{code}/buildings` |
| `roads`, `water` | `tiles/{code}/features` (build เดียวกัน จึงมีเวลาเดียวกันจริง ๆ) |
| `trees` | `tiles/{code}/landcover` |

**ห้ามใช้ mtime ของไฟล์ใน `apps/web/public/aoi/**`** โฟลเดอร์นั้นถูก track ใน git
ทุกไฟล์จึงมี mtime เท่ากับตอน `git checkout` ไม่ใช่ตอนสร้าง artefact การเขียนค่านั้น
ลง manifest คือการ ship เวลาที่แต่งขึ้น

`terrain.bin` (overview), `hillshade.png` และ `boundary.geojson` ถูก track เหมือนกัน
เวลาสร้างจริงของทั้งสามหายไปแล้ว — `hillshade.png` กับ `boundary.geojson` จึง **ไม่มี
provenance entry เลย** ส่วน `terrain.builtAt` คือเวลาของ **build run** ที่ผลิต tile
pyramid ชุดนั้น (ไฟล์ overview ออกมาจากรันเดียวกัน) ไม่ใช่ timestamp ของตัวไฟล์เอง

### ชั้นที่ไม่มี entry — โดยตั้งใจ

- **`imagery` ไม่อยู่ใน `AoiProvenanceLayer` เลย** ภาพดาวเทียม (Esri World Imagery /
  EOX Sentinel-2 cloudless) เป็น tile service ที่ client ดึงสดรายไทล์ ไม่มี artefact
  ในชุดข้อมูลให้จดเวลา — จะจดก็ได้แต่ต้องแต่งขึ้น (แผนงานใน `docs/roadmap.md` เขียน
  imagery รวมไว้ด้วย นี่คือการตัดสินใจว่ามันไม่มีอยู่จริง ไม่ใช่การลืม)
- **ไม่มีโฟลเดอร์ tile → ไม่มี entry** เครื่องที่ไม่ได้ symlink ชุดข้อมูล 5.6 GB
  (เช่น clone ใหม่ หรือ CI) จะไม่มีโฟลเดอร์นั้น ชั้นนั้นต้องหายไปทั้ง entry
  **ห้ามแทนด้วย `generatedAt`, `manifest.version` หรือเวลาปัจจุบัน** — ฝั่ง web จะแสดง
  "ไม่ได้บันทึกเวลาที่ดึงข้อมูล" (`freshness.missing.staticReference`) ซึ่งเป็นความจริง

### `publishedAt` — เฉพาะแหล่งที่ประกาศเวลาไว้เอง

| แหล่ง | มี `publishedAt` ไหม | เหตุผล |
|---|---|---|
| OpenStreetMap (roads/water/buildings) | ✅ | หัวไฟล์ pbf มี `osmosis_replication_timestamp` ซึ่งเป็น instant ที่ต้นทางประกาศเอง — อ่านด้วย `osmium fileinfo -j` **ตอนรัน** ทุกครั้ง ห้าม hardcode |
| Copernicus DEM GLO-30 (terrain) | ❌ | ต้นทางบอกเป็นรุ่นของผลิตภัณฑ์ ไม่ใช่ timestamp |
| ESA WorldCover (trees) | ❌ | "WorldCover 2021" คือยุคของผลิตภัณฑ์ การขยายเป็น `2021-01-01T00:00:00Z` คือการสร้างความละเอียดที่ต้นทางไม่เคยบอก |

อ่านหัวไฟล์ pbf ไม่ได้ (ไม่มี osmium / ไม่มีไฟล์) → **ไม่เขียนฟิลด์นี้เลย** ไม่ใช่เดา

## 2. `checksums` และผลตรวจ `terrainIntegrity`

`checksums` เป็น sha256 (hex) ต่อไฟล์ คีย์เป็น path เทียบกับโฟลเดอร์ AOI ตอนนี้มี
`terrain.bin` ก้อนเดียว ซึ่งเป็นไฟล์ที่ป้อนชั้นข้อมูลที่คำนวณจากภูมิประเทศทั้งหมด

ฝั่ง client แฮชบัฟเฟอร์ **ที่โหลดมาอยู่ในหน่วยความจำแล้ว** ด้วย SubtleCrypto
(`scene/TerrainMesh.ts` → `verifyTerrainIntegrity`) ไม่มีการ fetch รอบสอง แล้วได้ผล
สามค่า:

| ค่า | ความหมาย | ป้ายใน legend | ปิดชั้นอะไร |
|---|---|---|---|
| `verified` | ตรงกับลายเซ็นใน manifest | ไม่แสดงอะไร | — |
| `unknown` | manifest ไม่ได้ประกาศลายเซ็น หรือเบราว์เซอร์ไม่มี SubtleCrypto (ไม่ใช่ secure context) | "ยังตรวจความถูกต้องของภูมิประเทศไม่ได้ (manifest ไม่มีลายเซ็น)" | **ไม่ปิดอะไรเลย** |
| `mismatch` | ไฟล์ที่โหลดมาไม่ใช่ไฟล์ที่ไปป์ไลน์สร้าง | "ตรวจสอบความถูกต้องของภูมิประเทศไม่ผ่าน — ชั้นพื้นที่ลุ่มต่ำใช้งานไม่ได้" | ดูหัวข้อ 3 |

`unknown` ≠ `mismatch` — "ยังไม่ได้ตรวจ" ไม่ใช่ "ตรวจแล้วไม่ผ่าน" manifest ส่วนใหญ่
ยังไม่มี checksum การปิดชั้นข้อมูลเพราะยังไม่ได้ตรวจ คือการกล่าวหาโดยไม่มีหลักฐาน

## 3. เกิดอะไรขึ้นเมื่อ `mismatch`

**หลักการ: DEM ที่เชื่อไม่ได้ ห้ามผลิตค่าภัยพิบัติต่อ แต่ห้ามทำให้แผนที่หายไปเงียบ ๆ**

ถูกปิด:

- **ชั้นพื้นที่ลุ่มต่ำ (แชนแนล R ของ overlay)** — `scene/hazardOverlay.ts` ล้างแชนแนล R
  เป็นศูนย์ผ่าน `suppressLowlandChannel()` ก่อนสร้าง texture ทั้งเส้นทางซิงโครนัสและ
  เส้นทาง Web Worker เรียกจุดเดียวกัน (`wrapOverlayField`) จึงแยกกันไม่ได้
- **`lowlandShare` กลายเป็น `null` ไม่ใช่ 0** — 0 อ่านออกมาว่า "ไม่มีพื้นที่ลุ่มต่ำเลย"
  ซึ่งเป็นคำกล่าวอ้างที่เราไม่มีสิทธิ์พูด
- **ชั้น "ระดับการเผชิญน้ำ (ภาพประกอบ)" (E10.4) ทั้งชั้น** — ทั้งส่วนที่ระบายลงบน
  ภูมิประเทศและหมุดรายสถานี ส่วนที่ระบายอ่านแชนแนล R นี้เป็นตัวคูณ (มีแต่ที่ลุ่มต่ำ
  เท่านั้นที่ติดสี) จึงดับตามไปเองเมื่อ R เป็นศูนย์ แต่ไม่ได้พึ่งผลข้างเคียงนั้นอย่างเดียว:
  `Map3DCanvas.tsx` ส่ง `null` เข้า `overlay.updateExposure()` ตั้งแต่แรกเมื่อผลตรวจเป็น
  `mismatch` (texture ของชั้นนี้ถูกล้างเป็นศูนย์ และ `uShowExposure` = 0) ส่วน **หมุด
  ไม่ได้ถูก gate ด้วยแชนแนล R เลยโดยตั้งใจ** — สถานีที่ "ไม่มีปัจจัยใดวัดได้" ต้องเห็นได้
  แม้อยู่บนที่ดอน — จึงต้องปิดด้วยเงื่อนไข `integrity !== "mismatch"` ตรง ๆ ที่นั่น
  เพราะระดับความสูงที่ใช้วางหมุดมาจาก DEM ก้อนเดียวกับที่เชื่อไม่ได้
- **อะไรก็ตามที่ gate อยู่บนแชนแนล R นี้ในอนาคต** จะถูกปิดตามไปด้วยแบบเดียวกัน ค่า
  `lowlandShare` เดินทางไปกับ `MapInfo` อยู่แล้ว (ยังไม่มีคอมโพเนนต์ไหนแสดงมัน)
  ตัวที่มาอ่านทีหลังจึงได้ `null` ติดมาด้วย ไม่ใช่ 0

**ไม่**ถูกปิด:

- **ภูมิประเทศฐาน** ยังเรนเดอร์ตามปกติ (พร้อมป้ายใน legend ว่าตรวจไม่ผ่าน) — การทำให้
  แผนที่ว่างเปล่าไม่ได้ทำให้ใครปลอดภัยขึ้น
- **แชนแนล G — ฮาโลรอบสถานีที่ตรวจวัดฝนหนัก/น้ำสูง** เป็นค่าที่ ThaiWater วัดมาจริง
  ไม่ได้มาจาก DEM
- **แชนแนล B — มาสก์ขอบเขตจังหวัด** มาจาก `boundary.geojson`

## 5. การรันไปป์ไลน์

**เส้นทาง build** — `npm run build:all -w apps/etl` (= `apps/etl/src/buildAllProvinces.ts`)
จดเวลาของแต่ละชั้นตอนที่ชั้นนั้นถูกเขียนเสร็จ และสคริปต์ tile รายชั้น
(`build:tiles`, `build:building-tiles`, `build:feature-tiles`,
`build:landcover-tiles`) เลื่อน `builtAt` เฉพาะชั้นที่ตัวเองเพิ่ง rebuild ผ่าน
`touchLayerProvenance()` ซึ่ง (ก) คำนวณ `checksums` ใหม่จากไฟล์ที่ ship อยู่จริงเสมอ
ไม่หิ้วค่าเก่ามาต่อ และ (ข) ปล่อย manifest ที่ **ยังไม่มี** provenance ไว้เหมือนเดิม
เพราะที่นั่นไม่รู้ `datasetVersion` ที่ถูกต้อง — ให้ `refresh:manifests` เป็นคนเติมทีเดียว

**เส้นทางรีเฟรช** — เติม provenance ลง manifest ที่ build ไปแล้ว โดยไม่ rebuild อะไร:

```bash
npm run refresh:manifests -w apps/etl -- --dry-run          # พิมพ์ว่าจะเปลี่ยนอะไร ไม่เขียนไฟล์
npm run refresh:manifests -w apps/etl                       # เขียนจริง
npm run refresh:manifests -w apps/etl -- --only=11,50        # เฉพาะบางจังหวัด
npm run refresh:manifests -w apps/etl -- --dataset-version=2026-08-20   # ปล่อยรุ่นใหม่
npm run refresh:manifests -w apps/etl -- --allow-version-reuse         # ทับรุ่นเดิมที่ยังไม่เคยอัป
```

ตั้งแต่ E9.2 การรีเฟรชยังเขียน `urlTemplate` ของ pyramid ทั้งสี่ชั้นให้ชี้ prefix
ของรุ่นด้วย (`/aoi/{code}/v/{ver}/{layer}/{z}/{x}_{y}.bin`) — เส้นทาง **build**
ยังเขียน prefix แบบไม่มีรุ่นเหมือนเดิม เพราะที่นั่นไม่รู้รหัสรุ่นที่ถูกต้อง
(เหตุผลเดียวกับที่มันไม่เติม provenance เอง) manifest ที่เพิ่ง build จึงชี้ prefix
เดิมจนกว่าจะรีเฟรช ซึ่งใช้งานได้ปกติเพราะ prefix เดิมไม่เคยถูกลบ (ดูหัวข้อ 7)

สคริปต์นี้ **idempotent**: ถ้า provenance ที่คำนวณได้เท่าของเดิมทุกฟิลด์ยกเว้น
`generatedAt` มันจะไม่เขียนไฟล์และคง `generatedAt` เดิมไว้ — `generatedAt` คือ
"เวลาที่เนื้อหานี้ถูกเขียน" การเลื่อนมันทั้งที่เนื้อหาไม่เปลี่ยนคือการรายงานงานที่ไม่ได้เกิดขึ้น

สคริปต์นี้ไม่ดาวน์โหลด OSM extract เอง ไม่มีไฟล์ = ไม่มี `publishedAt`

**ทั้งสองเส้นทางเรียกโมดูลเดียวกัน** (`apps/etl/src/provenance.ts`) จึงให้รูปร่างและ
กฎเดียวกันเสมอ เทสอยู่ที่ `apps/etl/src/provenance.test.ts` (รันด้วย `npm test` ที่ root
ซึ่งรวม `apps/etl` แล้ว)

## 7. prefix ของ tile แบบมีรุ่น และนโยบายเก็บ prefix เก่า (E9.2)

### URL สองแบบที่ต้องตอบ 200 ทั้งคู่

| แบบ | ตัวอย่าง | คีย์ใน R2 |
|---|---|---|
| แบบมีรุ่น | `/aoi/11/v/2026-08-17/terrain/5/12_34.bin` | `aoi/11/v/2026-08-17/terrain/5/12_34.bin` |
| แบบเดิม | `/aoi/11/terrain/5/12_34.bin` | `aoi/11/terrain/5/12_34.bin` |

ตัวอ่าน path มีตัวเดียวคือ `apps/web/worker/tilePath.ts` ซึ่งทั้ง Worker
(`worker/index.ts`) และ middleware ตอน dev (`apps/web/vite.config.ts`) ใช้ร่วมกัน
— ไม่งั้นสองที่จะค่อย ๆ เห็น "path ของ tile" ไม่ตรงกัน

**URL แบบมีรุ่นแปลงเป็นคีย์แบบมีรุ่นเสมอ** ห้ามตัด `v/{ver}` ทิ้งแล้วไปหยิบไฟล์
ของ prefix เดิมมาตอบ: นั่นคือการทำให้ชุดข้อมูลสองรุ่นกลายเป็นไบต์ก้อนเดียวกัน ซึ่ง
เป็นสิ่งที่ version-addressing มีไว้เพื่อกันพอดี ไม่มีไฟล์นั้นในรุ่นนั้น = **404
อย่างซื่อสัตย์**

**เฉพาะ AOI ที่รหัสเป็นตัวเลขสองหลัก** — `tilePath.ts` แมตช์ `(\d{2})` เท่านั้น
AOI สาธิต (`chiangmai-old-city`) จึงถูกคง `urlTemplate` ไว้ที่ prefix เดิมเสมอ
วันนี้มันไม่มี pyramid อยู่แล้ว แต่ถ้าวันหนึ่งมีขึ้นมา การเขียน prefix แบบมีรุ่นให้มัน
= 404 ทุกไทล์บน prod ขณะที่ dev ยังเขียว (dev อ่านจากดิสก์ ไม่ผ่าน Worker)
`retargetTileTemplates()` เป็นคนกันไว้ พร้อมพิมพ์เหตุผลออกมาหนึ่งบรรทัด

ตอน dev เป็นข้อยกเว้นที่ปลอดภัย: `apps/etl/data/tiles` มีชุดข้อมูลชุดเดียวและไม่มี
โฟลเดอร์ `v/` อยู่บนดิสก์ middleware จึงตัดรุ่นทิ้งแล้วอ่านไฟล์เดียวกัน (ทุกรุ่น
ชี้ไฟล์ที่เครื่องนี้มีจริง ซึ่งเป็นความจริงของเครื่องนี้) และ dev ไม่ได้ส่ง
`immutable` ให้ใคร — บน prod ทำแบบนั้นไม่ได้เด็ดขาด

### นโยบายเก็บ prefix เก่า: **ไม่ลบ ไม่มีกำหนด**

`aoi/{code}/{layer}/…` ทุกไฟล์ **ห้ามลบ** และไม่มีวันหมดอายุ เหตุผลเป็นเรื่อง
คณิตศาสตร์ของแคช ไม่ใช่ความชอบ:

- ทุก tile ถูกส่งด้วย `max-age=31536000, immutable` เบราว์เซอร์ที่เคยโหลด URL แบบ
  เดิมไว้จะยังยิง URL เดิมได้อีกหนึ่งปีเต็มหลังจากที่ manifest เปลี่ยนไปชี้รุ่นใหม่
  แล้ว (manifest ไม่ถูกแคชแบบนั้น แต่ tile ที่ค้างในแคชของ client ไม่ได้หายตาม)
- ลบไฟล์เก่าทิ้ง = client เหล่านั้นได้ 404 กลางแผนที่ ซึ่งคือ "ข้อมูลหายเงียบ ๆ"
  ที่กฎความซื่อสัตย์ของโปรเจ็กต์ห้ามไว้

ต้นทุนของการเก็บไว้คือค่า storage ของ R2 (~5.2 GiB ต่อชุด) ไม่ใช่ค่า request จึง
รับได้ — แต่รู้ตัวเลขไว้: ชุดที่สองพา storage ข้าม 10 GB ที่ R2 ให้ฟรี ส่วนที่เกินคิด
$0.015/GB/เดือน (≈ $0.08/เดือนต่อรุ่นที่เก็บเพิ่ม) ถ้าวันหนึ่งต้องลบจริง ๆ ให้ลบ **เฉพาะรุ่นกลาง ๆ ที่ไม่มี manifest ไหนชี้
และเก่ากว่า 1 ปีเต็ม** (อายุของ `max-age`) เท่านั้น — prefix เดิมที่ไม่มีรุ่นคือ
ชุดที่ client รุ่นเก่าที่สุดยังใช้อยู่ ห้ามแตะ

`scripts/verify-tiles.sh` ตรวจทั้งสอง prefix ในรอบเดียว และแยกรายงานว่า "prefix
เดิมไม่ผ่าน" กี่ path (ของเก่าหายไป = ร้ายแรง) กับ "แบบมีรุ่นไม่ผ่าน" กี่ path
(ยังไม่ได้ก๊อป หรือ Worker ที่ deploy อยู่ยังไม่รู้จัก `/v/`)

### ลำดับการปล่อยรุ่น

**เอกสารฉบับหลักของขั้นตอนนี้คือ [`docs/dataset-release.md`](./dataset-release.md)** — ที่นั่นมี
ทั้งห้าขั้น (build → checksum → upload → verify → manifest diff), เงื่อนไขก่อนเริ่ม, ที่อยู่ของคีย์
R2 เมื่อทำงานใน worktree และตารางการถอยรายขั้น ลำดับที่สำคัญขนาดนี้เก็บไว้สองที่ไม่ได้: ที่นี่เหลือ
ไว้แค่กฎที่เป็นเหตุผลของลำดับนั้น

> รุ่นต้องมีอยู่ใน R2 **ก่อน** ที่ manifest จะชี้ไปหามัน ไม่งั้นจะมีช่วงที่ client ขอ tile ของรุ่นที่
> ยังไม่ถูกอัป — และชื่อรุ่นที่ปล่อยไปแล้วห้ามใช้ซ้ำกับไบต์ชุดอื่นเด็ดขาด (`immutable` หนึ่งปี)

ทั้งกระบวนการรันด้วยคำสั่งเดียว ซึ่งบังคับลำดับนั้นแทนคนและหยุดทันทีที่ขั้นไหนไม่ผ่าน:

```bash
scripts/release-dataset.sh --version=2026-08-21 --dry-run   # พิมพ์ทุกขั้น ไม่แตะอะไรเลย
scripts/release-dataset.sh --version=2026-08-21 --copy      # ของจริง
```

**เงื่อนไขก่อนเริ่ม**: `siahra-web` ที่ deploy อยู่ต้องมี `worker/tilePath.ts` ของ E9.2
แล้ว เพราะทั้ง `--smoke` และ `verify-tiles.sh` ยิง HEAD ผ่าน Worker ตัวจริง — Worker รุ่นก่อนหน้า
ไม่รับ `/v/` แล้วโยนให้ asset layer ซึ่ง (วัดจริงบน prod 2026-08-20) ตอบ **`200 text/html`** คือ
หน้า `index.html` ไม่ใช่ 404 ทั้งที่ไบต์อาจถูกก๊อปขึ้นไปแล้ว การนับแค่สถานะ `200` จึงอ่านว่า "ผ่าน"
ให้กับรุ่นที่ยังไม่มีไบต์อยู่จริง — ทุกจุดที่ยิงไทล์จึงบังคับ `application/octet-stream` ด้วย
การ deploy โค้ดก่อนปลอดภัย เพราะ manifest ยังชี้ prefix เดิมอยู่ (`release-dataset.sh` ตรวจข้อนี้
ให้ก่อนเริ่ม พร้อมยิง path เดิมของไฟล์เดียวกันเป็นตัวคุมว่าอ่านค่าจากเน็ตได้จริง)

`--copy` ใช้ S3 CopyObject ภายใน bucket เดียวกัน จึงไม่ดึง 5.17 GiB ผ่านเครื่อง
ที่รัน สคริปต์สั่ง **ทีละชั้น** (`aoi/{code}/{layer}` → `aoi/{code}/v/{ver}/{layer}`)
เพราะปลายทางอยู่ "ใต้" ต้นทางถ้าสั่งทั้งจังหวัด — เป็นการก๊อปโฟลเดอร์เข้าไปในตัวเอง

**ข้อควรระวังที่วัดมาแล้ว**: prefix แบบมีรุ่นอยู่ข้างใน prefix เดิม
(`aoi/11/v/…` อยู่ใต้ `aoi/11/`) การ `rclone sync` ต้นไม้ในเครื่อง (ซึ่งไม่มี
โฟลเดอร์ `v/`) ขึ้นไปทับ จึงมองว่าไฟล์ทุกรุ่นเป็นขยะและลบทิ้งทั้งชุด —
`scripts/upload-tiles.sh` ใส่ `--exclude "v/**" --exclude "*/v/**"` ไว้ตายตัวใน
ชุดธงของคำสั่งที่ทำงานกับทั้งโฟลเดอร์ (และตั้งแต่รอบนี้ก็ไม่มี `sync` เหลือใน
สคริปต์แล้วด้วย — ดูหัวข้อถัดไป)

### สคริปต์อัปเป็น append-only ทั้งสอง prefix

นโยบาย "ห้ามลบ" ข้างบนไม่ได้อยู่แค่ในเอกสาร: `scripts/upload-tiles.sh` ใช้
`rclone copy` (ไม่ลบอะไรเลย) ทั้งกับ prefix แบบมีรุ่น **และ prefix เดิม** ไม่มี
`rclone sync` เหลืออยู่ในสคริปต์แล้ว เพราะ `sync` จะลบไฟล์ปลายทางที่ไม่มีในต้นไม้
ของเครื่องที่รัน — pyramid ที่ rebuild ใหม่แล้วบังเอิญขาดไทล์ไปหนึ่งใบก็ทำให้ไทล์
นั้นหายจาก R2 ได้ทันที ทั้งที่ client ที่แคชไว้ยังยิงหาอีกได้เต็มปีตาม `max-age`

**สิ่งที่แลกไป (ตั้งใจ)**: ไทล์ที่ถูกลบในเครื่องจะไม่ถูกลบตามบน R2 อีกแล้ว ของค้าง
